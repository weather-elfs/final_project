# ADR-0001: 저장소 아키텍처

- 상태: 승인
- 결정일: 2026-09-03

## 배경

이 프로젝트는 기상 데이터 수집·전처리·분석과 웹 대시보드를 함께 개발한다.
현재 대시보드 프레임워크, 패키지 관리 도구, 독립 배포 요구사항은 확정되지 않았다.
팀은 6명이며 대부분 비개발자이므로 초기부터 여러 패키지와 빌드 체계를 운영하면
학습·설정·통합 비용이 커진다.

## 결정

현재 저장소는 `src/weather/` 단일 Python 패키지를 사용하는 **모듈러 모놀리스**로
구성한다. 저장소가 하나라는 이유만으로 여러 배포 단위를 미리 만들지 않는다.

```text
src/weather/
├── ingest/        데이터 수집
├── preprocess/    정제·결측 처리
├── features/      파생 변수
├── analysis/      분석 로직
├── viz/           시각화 유틸리티
└── dashboard/     대시보드 프레임워크 확정 후 추가
notebooks/         탐색적 분석
scripts/           파이프라인 실행 진입점
tests/             자동 테스트
```

의존성 방향은 다음과 같이 제한한다.

- `dashboard`와 `scripts`는 `weather` 내부 모듈을 사용할 수 있다.
- 분석·전처리 모듈은 `dashboard`를 import하지 않는다.
- 노트북의 재사용 로직은 `src/weather/`로 옮긴 뒤 사용한다.
- 모듈 간 데이터 교환 형식은 `docs/conventions/data.md`의 스키마 규칙을 따른다.

## 다중 패키지 모노레포로 분리하는 조건

다음 중 하나가 실제 요구사항으로 확인되면 새 ADR을 작성하고 `apps/`와 `packages/`
구조를 검토한다.

- 대시보드와 파이프라인을 독립적으로 배포해야 한다.
- 서로 다른 Python 버전 또는 충돌하는 의존성이 필요하다.
- 구성 요소별 릴리스 주기나 소유 팀이 분리된다.
- 공통 라이브러리를 둘 이상의 독립 애플리케이션이 사용한다.

## 결과

- 초기 설정과 개발 흐름이 단순해진다.
- 패키지 경계 대신 모듈 의존성 규칙과 테스트로 결합도를 관리해야 한다.
- 분리 조건이 충족되기 전까지 다중 `pyproject.toml`이나 workspace 도구를 도입하지 않는다.
